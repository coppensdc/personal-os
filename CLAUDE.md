# Personal OS

A personal operating system: quarterly priorities, daily to-do's, a scratchpad, and (eventually) more modules, built as a static multi-page site. No build step, no framework — vanilla HTML/CSS/JS. **Live** at https://coppensdc.github.io/personal-os/ (GitHub repo: `coppensdc/personal-os`, public), reachable from any device including phone.

Last updated: 2026-10-03 (added Review — plan/push/lingering — + plan-for-a-day on To Do's items; earlier: removed Decisions/Weekly review, added Ideas + the weekly self-improvement run, To Do's Follow-ups)

## Structure

```
index.html            Landing page — quick capture, module list (order matches nav below); home.js/home.css
todos/index.html       To Do's module (fully built)
review/index.html      Review — give open to-dos a day, push to next week, flag lingering; writes into To Do's blob
notepad/index.html     Notepad module — collapsible topic sections, rich text, search, send-to-to-do
ideas/index.html       Ideas — queue of improvements for the weekly Claude run; ideas/log.js is its changelog
manifest.webmanifest   PWA manifest (add to home screen); icons in shared/icons/
shared/css/            tokens.css, base.css, components.css, nav.css, backup.css
shared/js/              storage.js, nav.js, backup.js, plan.js (week-plan rules shared by To Do's + Review)
```

## Conventions

- Each module is a folder with its own `index.html`, referencing the shared CSS/JS plus its own `<module>.css`/`<module>.js` when it has module-specific logic.
- Data persists in **Supabase** (project ref `seuqxfxjvrwoimdwmoau`), not `localStorage` (moved 2026-09-13 for cross-device sync). One row per module in a shared `app_state` table (`key text primary key, data jsonb, updated_at`), keyed by the same strings the old localStorage scheme used (`personal-os-rocks-v1`, `personal-os-todos-v1`, `personal-os-notepad-v1`) — each row's `data` holds that module's entire state blob, same shape as before. `shared/js/storage.js` exposes the same `loadState`/`saveState` API each module already called, so `todos.js`/`rocks.js`/`notepad.js` didn't need rewriting — only `boot()` in each became `async` (since `loadState` now awaits a network call) and each file's `boot(); render();` at the bottom became `boot().then(render);`. The Supabase URL + anon public key are hardcoded at the top of `storage.js` — safe to have in public client-side code by Supabase's design (the anon key only grants what RLS policies allow), but it does mean the `app_state` table's "anon full access" RLS policy (see project's Supabase dashboard → SQL Editor for the exact policy) makes all Personal OS data readable/writable by anyone who finds the site and looks at its JS source — acceptable tradeoff for a personal tool with no login, revisit if that changes. **Superseded 2026-09-27 — auth added:** every page is now gated by Supabase Auth (email magic link only — Supabase's default mailer doesn't allow editing the email template to include a typed code without custom SMTP, so there's no code-entry step). `storage.js` creates an `authReady` promise that resolves once there's a session; until then it injects a full-screen `.auth-overlay` sign-in form (styles in `components.css`). `loadState`/`saveState` and `backup.js`'s `collectAllData`/`restoreFrom` all `await authReady` before touching Supabase, so no data request goes out signed-out. Sign-in uses `shouldCreateUser: false` (only a user pre-created in the Supabase dashboard can sign in) and `flowType: 'implicit'` (so a magic link opened on a different device/browser than the one that requested it still works — PKCE would fail there). A "Sign out" button is appended to the nav by `storage.js` after sign-in (not by `nav.js`, which loads before `storage.js`). **Password sign-in** (added 2026-09-28) exists because an iOS home-screen app has its own storage separate from Safari and magic links always open in Safari — so the PWA can't be signed in by link. The overlay has a "Sign in with password" toggle (`signInWithPassword`); the password is set once, while signed in, from the Home page's "Sign-in for the home-screen app" disclosure (`sb.auth.updateUser`). The RLS policy is meant to be "authenticated AND `auth.uid()` = the owner's user id" — the anon policy is dropped; the exact SQL lives in the Supabase dashboard, not this repo. Magic-link redirects can't target `file://`, so local testing needs a local HTTP server (e.g. `python3 -m http.server`) with `http://localhost:<port>/**` added to the project's allowed redirect URLs. `supabase-js` is loaded via a `<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2">` tag before `storage.js` on every page that needs it.
- **Caveat inherited from the localStorage era, now moot for app data but still true of anything that ever goes back to `localStorage`:** it's scoped per exact origin/path — doesn't apply to Supabase, which is origin-independent.
- Shared top nav: each page sets `window.NAV_BASE` (relative path back to root) and `window.NAV_ACTIVE` (current module key) before loading `shared/js/nav.js`, which injects the nav bar into `<div id="os-nav">`. Nav order (and the Home page's module list, kept in sync manually) is: Home, To Do's, Review, Notepad, Ideas. On phones (≤520px) the nav is one horizontally scrolling row with the brand pill hidden; `nav.js` scrolls the active link into view, and `storage.js` repeats that after inserting Sign out (which narrows the row).
- **Shared date helpers live in `storage.js`** (moved out of `todos.js` 2026-09-28): `isoDate`, `todayISO`, `parseISODate`, `addDaysISO`, `daysBetweenISO`, `weekStartISO` (Monday of a date's week), `planWeekStartISO(iso?)` (the week being planned on that day — next week from Saturday on; used by Review + To Do's), `weekdayShort` — all in local-time `YYYY-MM-DD` strings (never `new Date('YYYY-MM-DD')`, which parses as UTC). Also `idTimestamp(id)`, which recovers creation time from a `uid()` (its first 8 chars are `Date.now()` in base 36).
- **Cross-module writes to To Do's** (Notepad's "To do" button, Home's quick capture) re-read `personal-os-todos-v1` with `loadState` at the moment of writing, never from a copy loaded at page boot, then `saveState` the whole blob. New items must match `addItem()`'s shape in `todos.js` (incl. `createdAt`). The old "stale tab overwrites these additions" problem is now mostly handled by live sync (next bullet); per-item rows remain the proper fix if it still bites.
- **Live sync** (added 2026-09-29): each module's whole state is one blob and `saveState` blindly overwrites it, so a long-open tab used to silently wipe newer saves from another device ("last save wins"). `watchState(key, fallback, onChange, {isBusy})` in `storage.js` keeps a page's copy current: it re-reads the row on a Supabase Realtime change (Realtime enabled for `app_state` via the `supabase_realtime` publication, done in the dashboard), on tab visible/window focus/online, and every 5 min while visible. Own-save echoes are skipped by tracking every `updated_at` the page loaded or wrote (`seenVersions`) — compared by equality, not `>`, since `updated_at` is client-clock time and devices can be skewed. A fetch overlapping one of our own in-flight saves is discarded and retried (it could return the pre-save row and revert us). `onChange` is deferred while `isBusy()` — default `pageIsBusy()`: window focused and an input/textarea/contenteditable has focus; To Do's also waits on the mark-done modal and drags, Notepad on section drags. Every module page plus Home calls it; modules re-run their normalize/migration step on the fresh blob, not `boot()`. Remaining gap: a remote change arriving *while* you're mid-edit is overwritten when that edit commits — a check-before-write on `updated_at` would close it.
- Design tokens live in `shared/css/tokens.css` — reuse these rather than hardcoding values so modules stay visually consistent.
- Reusable UI classes (`.row`, `.status`/`.status-dot`, `.icon-btn`, `.progress-bar`, `.empty-state`, `.add-item-btn`, `.list-row`, `.arcade-divider`) live in `shared/css/components.css`. `.card` still exists as a class name (kept on some elements for historical reasons) but is now a no-op — see Design system below.

## Design system — "Amalfi" (adopted 2026-07-18)

Applied from a text design handoff (no visual reference file was available in this session — implemented directly from the written spec, then verified by rendering).

- **Palette**: white background; forest (`--text: #0E2C2B`) for headings/primary text; coral (`--accent: #F26B43`) as the *one* accent color (active states, links, progress fill, checked checkboxes, priority ring); amber (`--amber: #FBAE40`) reserved *only* for the Rocks "off track" status — not reused elsewhere (e.g. To Do's priority marker uses coral, not amber, to keep amber's meaning singular).
- **Fonts**: `Bricolage Grotesque` (weights 300/400/500 only — never use 700/bold, it's not loaded and would fake-bold) for UI, `Instrument Serif` italic for the page eyebrow line. Loaded via `@import` at the top of `shared/css/tokens.css` (requires internet access when the page loads — a deliberate tradeoff to avoid repeating `<link>` tags across every page).
- **No cards/shadows**: rows are separated by 1px hairlines (`.row` class: `border-top`, `:first-child` gets none) instead of boxed/shadowed cards. `.card` was repurposed to neutralize the old boxed look rather than ripping it out of every template's class list.
- **Status pattern**: a 7px dot + sentence-case word (`.status` + `.status-dot`, classes `status-coral`/`status-amber`/`status-neutral`), no pill background. Used by Rocks; reusable for any future status needs.
- **Arcade divider**: a scalloped inline SVG background (`.arcade-divider`, coral ~55% opacity) placed between the page header and the content list on every page. The nav bar has its own similar scalloped pattern along its bottom edge (coral ~35% opacity) plus each nav link/brand sitting in its own coral-tint pill.
- **Icons**: all hand-authored inline SVGs, 1.5px stroke, `currentColor`, no fill — no emoji anywhere (the old ✓ ◎ ◆ ◇ ✎ module glyphs were replaced with line icons).
- **Sentence case everywhere** — no uppercase labels/letter-spacing tracking (e.g. "This quarter", "On track", not "THIS QUARTER"/"On Track").
- Rocks' header uses the full pattern: italic eyebrow, big title, completion % baseline-aligned top-right, a 2px hairline progress track, then a plain-language counts line ("x/y rocks complete   x/y milestones done") — this replaced the old boxed "overview card" stat tiles entirely. Other modules keep the simpler eyebrow/title/date header (no % metric — there wasn't a natural one to force onto them).

## Module notes

### Rocks / Agents (removed 2026-09-28)
Deleted from the repo, nav, and Home page — Rocks now live in Ninety (the team's EOS tool) and agents in Langdock, so both modules were dead weight. Rocks' data row (`personal-os-rocks-v1`) was left in Supabase untouched; the module code is recoverable from git history (last present in commit `7f9d427`). Rocks was an EOS-style quarterly-priorities module (rocks with milestones, status cycling on-track → off-track → complete); Agents was only ever a "coming soon" stub.

### To Do's
- Page uses a wider container than the rest of the site: `.container--wide { max-width: 900px }` (defined in `todos.css`, applied only on `todos/index.html`'s `#app` div) — the shared 700px `.container` in `base.css` is untouched so every other module stays at the original width.
- **Blocks, not hardcoded columns** (as of 2026-07-23): `state.blocks` is an array of `{id, name, color, today, followups, done, followupsOpen, doneOpen}` — you can add, rename, and delete blocks freely, not just the original two. Ships with "Work" and "Personal" by default.
  - **Add**: quiet "+ Add a block…" input pinned below the last row.
  - **Rename**: the block title is itself an always-editable `<input>` (same pattern as to-do item text) — click in, type, blur or Enter commits.
  - **Delete**: hover-revealed trash icon in the block header, guarded by a native `confirm()` (same destructive-action pattern as the Backup widget's Restore) since it permanently removes that block's to-dos and Done history.
  - **Layout** (revised 2026-08-27): blocks render `state.gridCols` per row (2/3/4, toggle in the page header — see "View controls" below), always an even split within a row via plain flex `gap` — the old shared drag-resizer (`state.colWidthPct`) was removed entirely. `renderColumn()` no longer takes a "full width" flag: a partial last row (e.g. 1 leftover block in a 3-column grid) is left to plain `flex: 1 1 0`, which naturally fills 100% when it's the row's only child — this replaced an earlier explicit `.todo-column--full` special case now that column count isn't fixed at 2.
  - **Reordering blocks** (added 2026-08-27, moved to the header's right side alongside delete/color-dot later the same day so the title stays flush left): a hover-revealed grip handle (`.todo-block-handle`) drags a whole block to a new position via native HTML5 DnD — separate drag namespace (`blockDragging` in `todos.js`) from the existing item-level DnD (`dragging`), so the two never conflict even though block drop targets are the same `<section>` elements that contain the item lists. Dropping inserts the dragged block immediately before whatever block it's dropped on; order is just `state.blocks` array order, persisted like everything else.
  - **Migration**: `migrateToBlocks()` in `todos.js` upgrades a pre-existing save (top-level `personal`/`work`/`workPct` keys) into the blocks array on first load, then deletes the old keys and persists. The migration check deliberately keys off `state.personal` existing (the old shape), **not** off `state.blocks` existing — `loadState()`'s shallow merge (`{...DEFAULT_STATE, ...saved}`) means `state.blocks` is already populated from `DEFAULT_STATE` even for an old-format save that has no `blocks` key at all, so checking `if (state.blocks) return` would skip migration and silently replace real data with two empty default blocks. Caught this in testing before it shipped — any future migration in this codebase should key off the *old* shape's presence, never the *new* shape's, when `loadState` is involved.
- Each block is a **single ongoing "Today" list** (not day-by-day columns) — deliberately simpler than the notebook's literal day-flip, chosen so items just sit until checked off or moved to Follow-ups.
- **Priority**: toggle via the item menu (see below) — shows as a coral ring around the (circular) checkbox plus medium-weight text, echoing "circling a checkbox" in a paper notebook. (Uses coral, not amber — see Design system note above.) Toggling calls a full `render()` (not a surgical DOM patch, unlike most other per-item toggles) specifically so the **Important** summary panel picks up the change immediately.
- **Popovers** (added 2026-08-27): `openPopover(popoverId, anchorEl, innerHtml, extraClass)`/`closePopover()` in `todos.js` are a shared helper for any small anchored dropdown — currently used by the item menu and the block color picker (both below), and worth reusing for any future one rather than re-deriving the positioning/click-outside logic. A popover is appended straight to `document.body` (not nested in the row/header) alongside a full-viewport invisible `.todo-item-menu-catcher` (click-outside-to-close), positioned via `getBoundingClientRect()` on the anchor button with `position: fixed` (no scroll-offset math needed, unlike `position: absolute`) — appending to `body` avoids clipping from any ancestor's layout, matching the existing "Mark done" modal's append-to-body pattern. Because popovers live outside `#app`, `render()` calls `closePopover()` first thing, so a stray open popover never survives a re-render holding stale item/block references (e.g. after a drag-reorder while one was open elsewhere). Only one popover is ever open at a time, tracked by `openPopoverId` (e.g. `'item:<id>'` or `'color:<blockId>'`); the anchor button gets a `.menu-open` class for the duration so it can stay visually "pressed" even after mouse-hover would otherwise fade it.
- **Item menu** (added 2026-08-27, replacing four always-hover-revealed icon buttons per row): a single kebab button (`.todo-kebab`, three dots) opens a popover with Priority, Move to Follow-ups (or Move back to Today), Due date, Notes, Add sub-task, and Delete — done because four separate icons ate too much row width, especially at 3-4 grid columns. The kebab itself picks up `.active` styling (coral) whenever the item is priority-flagged, has a due date set, *or* has notes, so that state stays glanceable without opening the menu.
- **Notes** (added 2026-08-28, revised same day to live entirely inside the popover rather than the row): `item.notes` is a plain string (default `''`), never rendered on the main row — its only surface is a `<textarea>` inside the item's kebab popover, collapsed by default and expanded only by clicking the "Notes" row (`toggleNotesEditor()` toggles an `.open` class and calls `repositionPopover()` since the menu grows taller). `repositionPopover()` is `openPopover()`'s original position math pulled out into its own function specifically so notes-expansion could reuse it without re-triggering the popover's same-id-toggles-closed behavior. Because the whole notes editor lives inside the popover, the "empty notes should disappear on click-away" behavior needs no special-case code — the existing outside-click catcher (`closePopover()`) already removes the entire popover, notes included, regardless of content. `onNotesChange()` persists on blur/change without a full `render()` (matches `onSubTextChange`) — a full render would call `closePopover()` mid-interaction, which would yank the popover out from under a click on another menu item (e.g. Priority) that blurs the notes textarea first. The kebab button itself still picks up `.active` when `item.notes` is non-empty (same glanceable-state mechanism as priority/waiting/due date) — that's the only indicator that notes exist; it's intentionally not surfaced in the Summary panel.
- **Sub-tasks: auto-collapse when opened empty** (added 2026-08-28): clicking "Add sub-task" from the kebab menu still sets `item.subtasksOpen = true` and reveals the inline sub-tasks section on the row (unchanged), but now also registers a one-shot, capture-phase `document` click listener (`watchForEmptySubtasksClose()`, armed via `addSubtaskUI()` with a `setTimeout(...,0)` so it doesn't immediately fire on the same click that opened it) that collapses the section back (`subtasksOpen = false`) the next time a click lands outside that item's row — but only if no sub-task was actually added (`item.subtasks.length` stays 0). If a sub-task exists, the section stays visible regardless of `subtasksOpen`, same as before (`hasSubtasks || subtasksOpen` gate in `renderRow()`).
- **Due date** (added 2026-08-27): `item.dueDate` is a plain `YYYY-MM-DD` string (or `null`), set via a native `<input type="date">` inside the item menu (the `Due date` row — a `<label>` so clicking its text/icon, not just the input, opens the native picker). Deliberately not shown anywhere on the main to-do row itself — its only surface is the **Important** summary panel (below). Date math (`todayISO()`, `addDaysISO()`, `isDueSoon()`, `formatDueLabel()` in `todos.js`) is done entirely in `YYYY-MM-DD` string space rather than `Date` object arithmetic, specifically to sidestep the classic `new Date('2026-08-30')` UTC-parsing/timezone-shift bug — ISO date strings also happen to sort correctly with plain string comparison, which the summary's sort relies on.
- **Important summary now also surfaces due dates** (revised 2026-08-27): `collectImportantItems()` includes an item if it's priority-flagged **or** its `dueDate` is today/tomorrow (`isDueSoon()`) — so a due-soon item shows up even if never flagged, addressing the original panel's blind spot (a deadline you forgot to flag). The list sorts by `dueDate` ascending (undated items sort last, via a `'9999-99-99'` sentinel key) rather than by flag/insertion order like before. Each row shows a `formatDueLabel()` string ("Due today" / "Due tomorrow" / "Due Aug 30") when a due date is set, colored coral (`.todo-important-due.soon`) only when it's actually due soon — a flagged item with a due date further out still shows the date, just muted. **Bold vs. not is the flagged/unflagged distinction, not date-related**: `renderImportantRow()` only applies the `.priority` class (bold text, coral check ring) when `item.priority` is true, even though the row is also rendered for due-soon-but-unflagged items — this was a real behavior change from the panel's original assumption that every row in it was flagged, so both the checkbox and textarea's `priority` class became conditional rather than unconditional.
- **Block color** (added 2026-08-27): each block can be assigned a custom color from a fixed 7-swatch palette (`BLOCK_COLORS` in `todos.js` — coral/amber/teal/slate/plum/olive/rose, all muted to match the Amalfi palette rather than saturated) via a small always-visible dot button (`.todo-block-color-dot`, left of the title, empty ring when unset) that opens a popover of swatches plus a "Default (no color)" reset. Deliberately scoped to two effects only, both derived from the one stored hex (`block.color`) via CSS custom properties set inline on the `<section class="todo-column">` (`--block-color` full-strength, `--block-tint` a 7%-alpha rgba computed by `hexToRgba()`) so they inherit down to descendants without extra plumbing: the block's title text color (`--block-color`, replacing plain `var(--text)`), and that block's even-row zebra-stripe background (`--block-tint`, replacing the previously page-wide fixed `var(--accent-faint)` — a block with no color falls back to that same original coral tint, so existing blocks look unchanged until a color is chosen). Deliberately does *not* touch item-level status colors (priority ring, waiting wash, hover states) — those stay the fixed coral/neutral they've always been, so block identity and item status remain visually distinct meanings rather than competing for the same color channel.
- **Summary panel** (added 2026-08-27 as "Important", renamed to "Summary" later the same day — user-facing label only, internal class/function names (`.todo-important-*`, `renderImportant()`, `collectImportantItems()`, etc.) were left as-is since they're not visible and renaming them would've been pure churn): a full-width section between the header and the block grid, listing every item across every block (Today and Follow-ups, not Done) that's priority-flagged or due soon (see Due date below). Each row has its own checkbox (opens the same "mark done" modal as the main lists), wrapping editable text (edits write back to the same underlying item), and a small tag showing the source block's name — clicking the tag scrolls that block into view and flashes it. Shows a quiet empty state rather than collapsing away, so the layout doesn't jump as you flag/unflag things. **Flagged items are indicated only by the coral ring on the checkbox** (`.todo-check.priority`) — the row text itself deliberately stays regular weight (the `.priority` class was removed from the row's `<textarea>`, though it's still applied to the checkbox) after the bold text was found to compete for attention with the due-date label on due-soon rows.
  - **Manual reorder** (added 2026-09-01): a hover-revealed grip handle (`.todo-important-handle`, left of the checkbox) drags a row to a new position within the panel via native HTML5 DnD — its own namespace (`summaryDragging`), separate from item-level (`dragging`) and block-level (`blockDragging`) drag state, following the same one-drag-kind-per-element-type pattern as those two. Default order is still due-date ascending (`collectImportantItems()`'s base sort, unchanged); dropping a row persists the *entire current on-screen id order* as `state.summaryOrder` (`reconcileSummaryOrderFromDom()`), which then takes priority over the due-date sort on every future render — `collectImportantItems()` places `summaryOrder` ids first (in that order), then appends any item not yet in `summaryOrder` (newly flagged/newly due-soon items) afterward, still due-date-sorted among themselves. This means a manual order is sticky per-id but not exhaustive: an item that drops out of the panel (completed, unflagged, no longer due soon) and later reappears has lost its old manual slot and re-enters at the back of the list until dragged again.
- **Wrapping text** (added 2026-08-27): to-do text (main rows and sub-tasks) renders as an auto-growing `<textarea rows="1">` instead of a single-line `<input>`, so long to-dos wrap instead of scrolling/truncating — rows are no longer uniform height. `autoGrowTextarea()`/`initAutoGrow()` in `todos.js` handle sizing (height set from `scrollHeight` on every `input` event, and once per element after every full `render()`, since a fresh `innerHTML` swap needs its height recomputed). Enter still commits/blurs rather than inserting a newline, matching the old input's behavior. `onTextChange`/rendering assumes text has no real need for literal newlines — this only prevents accidental hard line breaks, not multi-line composition.
- **View controls** (added 2026-08-27): two small segmented button groups (`.todo-toggle-group`, hairline-bordered — a deliberate one-off exception to the "no boxes" rule since these are controls, not content) in the page header, right-aligned under the date. **Columns** sets `state.gridCols` (2/3/4 — `setGridCols()`), driving `renderRows()`'s grouping and also widening the page container itself (`#app.todo-cols-3`/`.todo-cols-4` in `todos.css` bump `max-width` past the base 900px, toggled via classList in `render()`, since more columns need more horizontal room to stay legible). **Text size** sets `state.fontSize` (`sm`/`md`/`lg` — `setFontSize()`), which `render()` writes as the `--todo-font-size` CSS custom property on `#app` (`FONT_SIZES` map in `todos.js`); to-do text, quick-add inputs, and secondary text (sub-tasks, done notes) all read this variable rather than a hardcoded `font-size`, with secondary text offset `-.0625rem` off the main size so the size hierarchy holds at every step. Meant to be used together — smaller text is what makes a 3 or 4-column grid actually readable on a wide monitor.
- **Follow-ups** (added 2026-10-01, replacing the 2026-09-28 "Waiting for answer" flag and its sort-to-top): each block has a second open list, `block.followups` (collapsible via `followupsOpen`, open by default), under Today — for things already handed off: waiting on a reply, a team review, or someone you delegated to. `OPEN_SECTIONS = ['today','followups']` is what every cross-section loop uses (drag reconcile, Summary, backfill). Membership is marked by `item.waiting = true` + `item.waitingSince` (`YYYY-MM-DD`, the day it went in); `markFollowup()` stamps/clears both whenever an item enters or leaves — via the kebab menu ("Move to Follow-ups" / "Move back to Today", `moveItem()`), the section's own quick-add, or a drag (`reconcileBlocksFromDom` re-stamps by destination list). Follow-up rows show a meta line under the text ("Since Sep 24 · 7d · Due Oct 3"): age goes coral at `WAITING_NUDGE_DAYS` (5), due date coral when due soon; follow-ups that old or due soon also enter the Summary, tagged "· Follow-up". `migrateWaitingToFollowups()` (in `normalizeState`) moves any `waiting` item still in Today into Follow-ups — keyed off that old shape, so it also catches items flagged by a tab still running older code. Items also carry `createdAt` (ISO); `backfillItemDates()` fills it from the id via `idTimestamp()` for old items.
- **Due soon includes overdue** (2026-10-01): `isDueSoon()` is `dueDate <= tomorrow`, so overdue items stay in the Summary ("Was due Sep 30") instead of silently dropping out the day after. On phones (≤640px) Summary rows wrap their labels/tag under the text instead of squeezing it.
- **Backlog removed** (2026-10-01) to free up space. `migrateBacklogToToday()` (runs in `normalizeState` before the waiting migration) appends any items in an old `backlog` array to the bottom of that block's Today list, then deletes the `backlog`/`backlogOpen` keys. It keys off those old keys being present, so it re-runs if a tab still on older code re-adds them.
- Drag-and-drop (native HTML5 DnD) reorders within a list, moves items between Today and Follow-ups, **and moves items across blocks entirely** (cross-block dragging added 2026-08-27 — originally scoped per block only). `onDragOver` no longer gates on `dragging.col !== list.dataset.col`, so a dragged item can be dropped into any list in any block. The commit-to-state step (`reconcileBlocksFromDom(sourceCol, targetCol)` in `todos.js`, replacing the old single-block `reconcileColumnFromDom`) rebuilds every `OPEN_SECTIONS` list for the source block, the destination block, or both (when they differ) purely from current DOM order — via a **global** by-id map spanning every block's items, not just the two involved, because a dragged item's own `data-col`/`data-section` attributes go stale the instant `onDragOver` physically relocates its DOM element into a different list (native DnD moves the actual node, it doesn't clone), so the reconcile can't trust those attributes and instead determines an item's new home purely from which list container it's physically inside when the drop fires.
- Checking a to-do's checkbox (in Today or Follow-ups) opens a modal asking what you actually did; confirming moves the item out of its list and into a collapsible **Done** section (per block, underneath Follow-ups) with that note and a completed-date stamp attached — an append-only archive, not just a strikethrough. Cancel/Escape/backdrop-click abandons the action with no state change. Delete on a Done row removes it from the archive permanently.

- **Plan for a day / push to next week** (added 2026-10-03, set mainly from Review): three additive per-item fields, no migration (absent = not set), rules in `shared/js/plan.js` (loaded by To Do's and Review so both apply the same ones): `plannedFor` (`YYYY-MM-DD` you mean to *do* it — separate from `dueDate`, the deadline; stays on items moved to Done so "planned done" counts work), `deferredUntil` (the Monday it was pushed to — `isPushed()` while that's after the plan week start, so pushed items come back on the Saturday before) and `deferCount` (times pushed). `isLingering()`: a Today item open `LINGER_DAYS` (21) days or pushed `LINGER_PUSHES` (2) times, and not slipped/pushed/planned this week — pushing never hides an item for good, each push makes it louder. Kebab menu: "Plan for" (Today) / "Chase on" (Follow-ups) and "Push to next week" / "Bring back to this week"; pushed rows are muted with "Pushed to week of Oct 12" in the meta line. Rows show it in the meta line under the text (`renderItemMeta()`, which replaced `renderFollowupMeta()` — Today rows only get a meta line when planned or pushed): "Today"/"Tomorrow"/weekday/date, or coral "Slipped from Mon" once the day has passed and it's still open (`isBehind()`). The **Summary** now also includes items planned for today and slipped items, sorted slipped → planned today → rest (then due date; manual `summaryOrder` still wins), and a plan line under its title: "Week of Oct 5 · 3/8 planned done · 2 slipped · 4 lingering" plus a link to Review that turns coral ("Do your review") when `state.lastReviewAt` doesn't cover the current plan week (`needsReview()`).

### Review (added 2026-10-03; Monday is the default, but meant to be done any time)
`review/` — not a separate data row: it reads and writes `personal-os-todos-v1` directly (whole-blob `saveState`, kept current by `watchState` like every page). Never runs To Do's migrations or reshapes the blob; it only sets the plan fields above, the top-level `lastReviewAt` (`YYYY-MM-DD`, stamped by "Finish review", which can be pressed any day), and can delete lingering items. ### Notepad
Rich-text notes (contenteditable + `document.execCommand` toolbar: bold/italic/underline/bullets/numbers) organised into **collapsible topic sections** (added 2026-09-28).
- State: `{ sections: [{id, title, html, open, updatedAt}] }` under `personal-os-notepad-v1`. `migrateToSections()` wraps a pre-sections save's single `text` blob into one "Notes" section — keyed off `sections` being absent (old shape), per the To Do's migration lesson; `loadState` is called with an empty fallback so `sections` can't be pre-filled by the merge.
- One shared toolbar at the top acts on whichever section editor currently has focus (`activeEditor()`); buttons `preventDefault` on mousedown so clicking them doesn't steal focus/selection from the editor.
- Section header: chevron toggle (persisted `open`, so collapse state syncs across devices), always-editable title `<input>` (To Do's block-title pattern), muted "Edited …" stamp (updated live on input without re-render), hover-revealed delete (native `confirm()` only if the section has content) and grip handle for drag-reorder (native HTML5 DnD, `sectionDragging`; hidden on touch since HTML5 DnD doesn't fire there). "Collapse all / Expand all" sits at the toolbar's right. "+ Add a section…" input at the bottom (To Do's "Add a block" pattern).
- Typing in an editor persists on every input but never calls `render()` — only structural changes (add/delete/toggle/reorder) re-render, so the caret isn't lost mid-typing. `onAddSectionKey` must `preventDefault()` the Enter: focus moves to the new editor during keydown, and the Enter's default action would otherwise land there as a stray blank line (caught in testing).
- Editors are hairline-left-bordered (coral on focus) rather than boxed, matching the no-cards design rule.
- **Search** (added 2026-09-28): search box above the toolbar filters sections by title/text and force-opens matches (without touching persisted `open`; chevrons disabled while searching). `render()` builds the page shell once and `renderSections()` re-renders only the list, so typing in search never loses focus. Matches are painted with the CSS Custom Highlight API (`CSS.highlights`, `::highlight(notepad-search)`) — deliberately not `<mark>` tags, which would get saved into the note HTML. Browsers without it still filter, just unpainted. Escape clears.
- **Insert date**: calendar toolbar button or Ctrl/Cmd+; inserts "Sep 28, 2026 — " via `execCommand('insertText')`.
- **Send to To Do's**: select line(s), click "To do", pick a block → each non-empty selected line becomes a Today item in that block (see cross-module writes convention above). The selection is also cached in `lastSelectionText` on `selectionchange` because on touch a toolbar tap can clear the live selection; the cache is cleared on any pointerdown/keydown inside an editor so a stale selection is never sent.

### Backup (shared widget, not a nav module)
A small pill in the bottom-right corner of every page (`shared/js/backup.js` + `shared/css/backup.css`), added 2026-07-18 in response to the risk that `localStorage` has no durability — clearing browser data, a profile reset, or a new browser profile wipes everything with no recovery path. **Updated 2026-09-13**: `collectAllData()`/`restoreFrom()` now read/write the Supabase `app_state` table (via the same `sb` client from `storage.js`) instead of scanning `localStorage` — the app's real data lives in Supabase now, so a snapshot of `localStorage` would've silently been empty. The widget's own metadata (connected folder name, last-backup timestamp) still lives in `localStorage`, which is fine since that's per-device UI state, not app data.
- Uses the File System Access API: click the pill → "Choose folder" → pick a folder once via `window.showDirectoryPicker`. The handle is persisted in IndexedDB (`personal-os-backup` DB), not `localStorage` (handles aren't JSON-serializable).
- **Recommended destination**: `OneDrive - Expedition Growth Capital\Documents\Claude\Personal OS - backup` — cloud-synced, so it survives this machine dying, unlike the project's own `backup/` folder (which is just a local subfolder and was the initial, less durable choice made before this was raised). Picking the folder is a manual one-time step done via the native OS picker in the user's real browser — not something Claude can do on the user's behalf.
- Writes a dated snapshot `personal-os-backup-YYYY-MM-DD.json` (every `personal-os-*` `localStorage` key) the first time the app is opened each day — not on every keystroke — then deletes any snapshot file older than 14 days. Rolling dated snapshots were chosen over a single continuously-overwritten file specifically so a bad edit or accidental delete still leaves recent days' snapshots intact to roll back to.
- Chrome/Edge only (File System Access API isn't supported in Firefox/Safari) — the widget shows a disabled "Backup unavailable" pill in unsupported browsers rather than failing silently.
- **Restore UI** (added 2026-07-18): "Restore…" button in the connected panel lists snapshots found in the backup folder (newest first, via the same `dirHandle.keys()` scan `pruneOldSnapshots` uses), picking one + confirming (native `window.confirm`, since this is destructive and there's no undo but another backup) overwrites every `personal-os-*` `localStorage` key from that file and reloads the page. Not testable in the in-app Browser preview pane — `showDirectoryPicker` doesn't work there (no OS-level dialog support in that sandboxed context), so the connect/restore flow needs a real Chrome/Edge tab with an already-granted folder to click through.

## Known quirks

- The in-app Browser preview pane treats this folder as outside its recognized "project folder" and serves a static snapshot on repeat navigations instead of live-reloading edited files during a session — it can even freeze CSS custom property values, not just script contents. Not an issue for a real browser tab. Workaround used during development: bust `<link>`/`<script>` src query strings from within the already-loaded page (or monkey-patch functions/objects in place) to force a live re-fetch without a full navigation.
- **`fetch()` of local files doesn't work reliably for the actual user** — the preview pane apparently allows it, but Dennis's real browser blocks `fetch()`/XHR between sibling `file://` files by default (each local file is its own origin). This bit the first Past Calls implementation (silently empty page, no console-visible error the user would easily spot). Any data a module needs to load from a file it doesn't inline directly should be loaded via `<script src="...">` assigning a `window.SOMETHING = {...}` global, never via `fetch()` of a local `.json`. Always sanity-check a new module by actually opening it as a real file in a normal browser, not just the preview pane, if it introduces any new loading mechanism.
- **`mcp__Claude_Browser__*` (the Browser pane) and `mcp__claude-in-chrome__*` (Dennis's real Chrome) are different browser instances with separate `localStorage`/`IndexedDB`** — writing or reading state through one is invisible to the other. This isn't specific to Past Calls (see that module's note above for the original case) — it also silently broke an attempted Rocks data import (2026-07-18): data was written via the Browser pane, and Dennis, checking his real browser, saw nothing. Before claiming to have read, written, or verified any page state, confirm which of the two Dennis is actually looking at, and use the matching tool.
- **Neither browser tool could actually render this module during the 2026-08-27 To Do's session** — the Browser pane confirmed the "static snapshot, scripts never execute" quirk above (`<script src>` tags present in the DOM but `render`/`escapeHtml`/etc. all stayed `undefined`, `#app` stayed empty), and `mcp__claude-in-chrome__navigate` mangled a `file:///...` URL into `https://file///...` (an extra `https://` prefix slapped onto a URL that already had a scheme), landing on a Chrome error page; typing the URL into the address bar via `computer{action:"key", text:"ctrl+l"}` + type + Return didn't visibly change the tab's URL either. Ended up shipping that session's changes on code review + `node --check` alone, without a real visual pass — flag this explicitly to Dennis rather than claiming a browser check happened, and ask him to eyeball it himself in his own browser.
